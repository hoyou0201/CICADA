# 할 일 나누기와 이슈 생성

목표는 **한 명이 막혀도 나머지가 멈추지 않고, 일을 빨리 끝낸 에이전트가 바로 다음 일을 집을 수 있는** 작업 구조다. 의존성은 꼭 필요한 것만 남기고 대부분을 병렬로 둔다. 일은 공용 풀이므로 **담당자를 미리 정하지 않는다.** 담당자는 에이전트가 일을 시작할 때 `AGENTS.md`의 작업 루프대로 생긴다. Plankton(https://plankton.hoyou.dev)이 이슈를 읽어 착수 가능/막힘/여유 있는 사람을 보여 준다.

## 시작 전에 확인

- `docs/BRIEF.md`의 기능 목록, 완료 조건, 데이터·화면 계약이 채워져 있고 사용자가 승인했는지. 아니면 `contest-plan`으로 돌아가자고 말하고 멈춘다.
- `gh auth status`가 정상이고 현재 레포가 올바른지.
- 이미 `[T`로 시작하는 이슈가 있으면(`gh issue list --state all --search "[T in:title"`) 중복 생성하지 않고 사용자에게 알린 뒤 건너뛸지 갱신할지 묻는다.

## 1. 작업 목록 만들기

BRIEF의 기능 목록을 작업으로 쪼갠다. 원칙은 이렇다.

- **크기:** 한 작업은 AI 에이전트가 **15~30분**에 끝낼 크기를 기본으로 한다. 45분을 넘으면 반드시 나눈다. 작을수록 하나가 막혀도 손실이 작고 일이 끝난 에이전트가 다음 일을 빨리 집는다. 반대로 10~15분보다 작은 일은 이슈를 관리하는 비용이 더 크므로 같은 영역의 다른 작업에 합친다.
- **순서:** 맨 앞은 골격과 계약(T1)이다. 공통 타입·라우트·전역 스타일·의존성·배포 설정을 여기서 정리한다. 계약이 있으면 기능 작업들이 샘플 데이터로 동시에 시작할 수 있다. 그 뒤 기능 작업들은 서로 의존하지 않게 병렬로 둔다. 통합, 배포, 발표 자료 같은 마무리 작업만 앞선 것들에 의존시킨다.
- **수정 경로:** 작업마다 수정할 경로를 적고 다른 작업과 겹치지 않게 한다. 겹쳐야 하면 그 두 작업에 의존을 걸어 순서를 정한다.
- **완료 조건:** 눈으로 확인 가능한 조건(정상·빈 결과·오류 중 해당하는 것).
- **예상 시간:** 라벨 `est:15m`, `est:30m`, `est:45m` 중 하나. 이보다 큰 일은 만들지 않고 나눈다. 추정은 참고용이다.
- **점검:** 순환 의존이 없는지, 의존이 사실은 불필요하지 않은지 확인한다.

## 2. 먼저 보여 주고 확인받기

이슈는 팀이 함께 보는 공유 상태이므로 만들기 전에 **작업 목록을 사용자에게 보여 주고 승인**을 받는다. 표에는 ID, 제목, 의존, 예상 시간, 수정 경로, 완료 조건을 넣는다. 가장 길게 이어지는 의존 경로가 있으면 같이 알린다.

## 3. 이슈 생성

승인 후 의존하는 순서(앞선 작업 먼저)대로 만든다. 번호가 필요해서다.

- 제목: `[T2] 입력 폼과 검증`
- 라벨: `est:*`. 레포에 `in-progress`, `est:15m`, `est:30m`, `est:45m` 라벨이 없으면 먼저 `gh label create`로 만든다.
- **담당자(assignee)는 지정하지 않는다.**
- 의존성: `gh issue create --blocked-by <번호,...>`로 GitHub 의존 관계를 만들고, 본문에도 `depends on #N` 한 줄을 적는다(Plankton이 둘 다 읽고 중복은 합친다).
- 본문 형식 (`.github/ISSUE_TEMPLATE/task.md`와 같다):

  ```
  ## 목표
  <사용자 관점의 동작>

  ## 수정 경로
  <파일 또는 폴더>

  ## 완료 조건
  - <정상 동작>
  - <빈 결과/오류 상태>

  depends on #<번호>
  ```

일부만 만들어지고 실패했다면 성공한 번호와 실패한 작업을 정확히 보고하고, 다시 실행할 때 중복되지 않게 이어서 만든다.

## 4. 마무리

- BRIEF의 "작업 이슈" 절에 `T1 #1`처럼 번호만 적는다. 상태와 담당은 이슈가 원본이므로 복사하지 않는다.
- 레포 루트에 `.plankton.yml`이 없으면 `.plankton.example.yml`을 바탕으로 팀원 GitHub 아이디와 동시에 진행할 작업 수(에이전트 수)를 사용자에게 묻고 만들자고 제안한다. 모르는 아이디를 지어내지 않는다.
- 생성된 이슈 목록, 지금 바로 착수 가능한 일(의존 없음), 만들지 못한 것을 짧게 보고하고, Plankton에서 이 레포를 연결하면 바로 보이며 에이전트는 `AGENTS.md`의 작업 루프로 일을 집으면 된다고 알려 준다.
