# 할 일 나누기와 이슈 생성

목표는 **한 명이 막혀도 나머지가 멈추지 않고, 일을 빨리 끝낸 에이전트에게 리더가 바로 다음 일을 줄 수 있는** 작업 구조다. 의존성은 꼭 필요한 것만 남기고 대부분을 병렬로 둔다. 일은 이슈 풀이므로 **담당자를 미리 정하지 않는다.** 담당자는 에이전트가 일을 시작할 때 `AGENTS.md`의 작업 루프대로 생긴다. Plankton(https://plankton.hoyou.dev)이 이슈를 읽어 착수 가능/막힘/여유 있는 사람을 보여 준다.

## 시작 전에 확인

- `docs/BRIEF.md`의 기능 목록, 완료 조건, 데이터·화면 계약이 채워져 있고 사용자가 승인했는지. 아니면 `contest-plan`으로 돌아가자고 말하고 멈춘다.
- `gh auth status`가 정상이고 현재 레포가 올바른지.
- 이미 `[T`로 시작하는 이슈가 있으면(`gh issue list --state all --search "[T in:title"`) 이미 만들어진 묶음은 건너뛰고 없는 묶음만 이어서 만든다. 같은 기능의 이슈를 중복 생성하지 않고, T 번호는 이어서 붙인다.

## 0. 모든 묶음을 한 번에 만든다

BRIEF 기능 목록의 **모든 묶음(확정 범위 + 스트레치)** 을 처음에 한 번에 이슈로 만든다. 리더를 계속 돌리지 않으면 다음 묶음을 만들 시점을 알려 줄 사람이 없다. 이슈가 미리 있어야 앞 일이 닫히는 순간 뒤 일이 착수 가능해지고 묶음 사이에 빈 시간이 생기지 않는다.

- 묶음 번호는 BRIEF 기능 목록의 "묶음" 열을 따르고, 이슈마다 `묶음:N` 라벨을 붙인다.
- **의존은 실제로 필요한 것만 건다:** 위에 쌓는 기능의 이슈, 같은 파일을 먼저 고치는 이슈, 그리고 각 묶음의 통합·점검 이슈에는 그 묶음의 기능 이슈들. 묶음 번호가 뒤라는 이유만으로 앞 묶음 전체에 의존을 걸지 않는다. 시작할 수 있는 일은 일찍 시작되게 하기 위해서다.
- 뒤 묶음 이슈는 아직 없는 코드를 가정하고 쓴다. 수정 경로는 T1 골격과 BRIEF 계약이 정한 구조를 따르고, 새 파일이 필요하면 새 경로를 적는다.
- BRIEF에서 새 기능 중단(80%) 이후로 배치된 기능은 만들지 않는다.
- **뒤 묶음 다듬기:** 사용자가 "다음 묶음 점검해줘"라고 하면 아직 시작하지 않은 이슈의 목표와 수정 경로를 현재 `main` 기준으로 고친다. 이슈를 새로 만들지 않고 본문만 고친다. 작업 에이전트도 수정 경로가 실제와 다르면 멈추고 코멘트한다(`AGENTS.md`).

## 1. 작업 목록 만들기

모든 묶음의 기능을 작업으로 쪼갠다. 원칙은 이렇다.

- **크기:** 한 작업은 **PR 하나로 끝나는 기능의 한 조각**(로직 / 화면 / 연결 / 디자인 / 마감 중 하나)이고 수정 경로는 보통 1~3개 파일이다. 사람이 하면 10~20분, AI 에이전트는 실측 몇 분이다. **비슷한 크기로 균일하게** 쪼개야 `contest-plan`의 일 수 계산과 Plankton의 종료 예측이 맞는다. 사람 기준 30분을 넘을 것 같으면 나눈다. 반대로 한 줄 수정처럼 작은 일은 지시·병합 비용이 작업보다 크므로 같은 영역의 다른 작업에 합친다. `contest-plan`이 기능마다 센 일 수와 크게 다르게 나오면(계획보다 절반 이하 등) 표에 그 차이와 이유를 적는다.
- **순서:** 첫 묶음의 맨 앞은 골격과 계약(T1)이다. 공통 타입·라우트·전역 스타일·의존성·배포 설정을 여기서 정리한다. 계약이 있으면 기능 작업들이 샘플 데이터로 동시에 시작할 수 있다. 그 뒤 기능 작업들은 서로 의존하지 않게 병렬로 둔다. 통합, 배포, 발표 자료 같은 마무리 작업만 앞선 것들에 의존시킨다.
- **수정 경로:** 작업마다 수정할 경로를 적고 다른 작업과 겹치지 않게 한다. 겹쳐야 하면 그 두 작업에 의존을 걸어 순서를 정한다.
- **완료 조건:** 눈으로 확인 가능한 조건(정상·빈 결과·오류 중 해당하는 것).
- **디자인 일:** BRIEF "디자인" 절의 디자인 시스템 이슈와 기능별 디자인 다듬기를 이슈로 만들고 `디자인` 라벨을 붙인다. 제목은 `[T12] 디자인: 목록 화면 다듬기`처럼 쓴다. 완료 조건에는 BRIEF 디자인 규칙 중 무엇을 맞췄는지와 정상·빈 결과·오류 상태 화면이 모두 같은 스타일인지 적는다. 토큰 파일을 고치는 일은 디자인 시스템 이슈뿐이고, 다른 디자인 일은 그 이슈에 의존한다.
- **예상 시간 라벨(`est:`)은 선택이다.** 기본은 붙이지 않는다. 일의 크기 차이가 눈에 띄게 클 때만 `est:5m`, `est:10m`, `est:20m`처럼 붙인다. 추정은 부풀려지기 쉬워서 계획의 근거로 쓰지 않는다.
- **점검:** 순환 의존이 없는지, 의존이 사실은 불필요하지 않은지 확인한다.

## 2. 먼저 보여 주고 확인받기

이슈는 팀이 함께 보는 공유 상태이므로 만들기 전에 **작업 목록을 사용자에게 보여 주고 승인**을 받는다. 표에는 ID, 묶음, 제목, 의존, 수정 경로, 완료 조건을 넣는다. 모든 묶음을 잇는 **경로 일 수, 전체 일 수, 예상 완료 시간**(`contest-plan`의 식, 주기는 BRIEF 시간표 값), 묶음별 이슈 수, 동시에 필요한 최대 에이전트 수(가장 넓은 단계의 일 수)를 같이 알린다. 예상 완료가 BRIEF의 "스트레치가 끝나는 시점"과 크게 다르면 이유를 적는다.

## 3. 이슈 생성

승인 후 의존하는 순서(앞선 작업 먼저)대로 만든다. 번호가 필요해서다.

- 제목: `[T2] 입력 폼과 검증`
- 라벨: `in-progress`, `묶음:N`, `디자인`이 레포에 없으면 먼저 `gh label create`로 만든다. `est:*`는 붙일 때만 만든다.
- **담당자(assignee)는 지정하지 않는다.** 일을 줄 때 리더가 지정한다.
- 의존성: `gh issue create --blocked-by <번호,...>`로 GitHub 의존 관계를 만들고, 본문에도 `depends on #N` 한 줄을 적는다(Plankton이 둘 다 읽고 중복은 합친다).
- 본문 형식 (`.github/ISSUE_TEMPLATE/task.md`와 같다):

  ```
  ## 목표
  <사용자 관점의 동작>

  ## 수정 경로
  <파일 또는 폴더>

  ## 완료 조건
  - <정상 동작>
  - <빈 결과/오류 상태>

  depends on #<번호>
  ```

일부만 만들어지고 실패했다면 성공한 번호와 실패한 작업을 정확히 보고하고, 다시 실행할 때 중복되지 않게 이어서 만든다.

## 4. 마무리

- BRIEF의 "작업 이슈" 절에 `묶음 1: T1 #1, T2 #2`처럼 묶음별로 번호만 적는다. 상태와 담당은 이슈가 원본이므로 복사하지 않는다.
- `.plankton.yml`은 선택이다. 없어도 Plankton은 담당자로 등장한 사람을 팀원으로 보므로 묻거나 만들지 않는다. 사용자가 원할 때만 `.plankton.example.yml`을 바탕으로 만들고, 모르는 아이디를 지어내지 않는다.
- 생성된 이슈 목록, 지금 바로 착수 가능한 일(의존 없음), 만들지 못한 것을 짧게 보고하고, Plankton에서 이 레포를 연결하면 바로 보이며 일은 `contest-lead`(리더 AI)나 사용자가 담당자와 `지시:` 코멘트로 에이전트에게 주면 된다고 알려 준다. 작업 에이전트는 스스로 고르지 않는다.
