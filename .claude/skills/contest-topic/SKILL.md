# 대회 주제 정하기

시간이 5~6시간뿐이라 처음 30분에 정하는 "무엇을 만들지"가 대회 전체를 좌우한다. 후보를 넓게 벌리기보다 **핵심 흐름 하나로 1분 안에 시연할 수 있는 작은 제품**을 고르는 게 목적이다.

## 시작 전에 읽을 것

`AGENTS.md`와 `docs/BRIEF.md`. BRIEF의 `미정`과 빈 칸은 미확인이다. 예시나 내 추정을 공식 규정으로 취급하지 않는다. 앱 스택이나 프레임워크는 여기서 정하지 않는다(다음 단계 `contest-plan`의 일).

## 모드 1: 실제 주제가 공개된 경우

1. **사실 수집.** 사용자가 준 주제 원문, 규정, 평가 항목, 남은 개발 시간, 발표 시간, 사전 코드·AI 도구·외부 API 허용 여부를 정리한다. 모르는 항목은 추측으로 채우지 말고 `미정`으로 두되, **후보 선택을 바꿀 것만** 사용자에게 묻는다(예: 평가 비중, 남은 시간). 질문은 한 번에 모아서 한다.
2. **후보 최대 3개.** 각 후보는 한 문장 요약, 대상 사용자와 겪는 문제, 1분 데모에서 보여줄 장면을 적는다. 하나로 가르는 기준은 BRIEF가 정한 네 가지다: 주제 적합성, 문제의 명확성, 시간 내 구현, 시연 가능성. 표로 비교하고 외부 서비스 의존이 큰 후보는 그 위험을 적는다.
   - **시간 내 구현은 너무 작은지도 본다.** AI 에이전트를 여러 개 쓰면 핵심 흐름만 있는 작은 제품은 1시간 안에 끝난다. 핵심 흐름 위에 단계적으로 쌓을 거리(기록 → 통계 → 요약, 추천 → 상세 → 즐겨찾기처럼 앞 결과를 쓰는 다음 기능)가 있는 후보를 낫게 본다. 후보마다 쌓을 거리를 두세 줄 적는다.
   - **시간을 다 채우려고 큰 제품을 고르지는 않는다.** 일이 많을수록 에이전트를 많이 띄워야 하고 사용량이 늘어난다. 연습 기준으로 이슈 90개 안팎(가장 긴 사슬 17단계 정도)이면 충분하고, 남는 시간은 점검·다듬기·발표 준비로 쓴다.
3. **추천 1개.** 이유를 말하고 사용자가 고르게 한다. 공식 규정과 내 추천을 섞어 말하지 않는다. 가장 작은 핵심 흐름으로 가치를 보이는 후보가 기본 추천이다.
4. **BRIEF 반영.** 사용자가 고른 뒤에만 `docs/BRIEF.md`의 "대회 사실" 표와 "제품을 한 문장으로"를 채운다. 공식 근거 칸에는 링크나 출처를 쓰고, 근거가 없으면 `미정`으로 남긴다. 다른 절은 건드리지 않는다.

## 모드 2: 연습용 주제를 만들어 달라는 경우

대회 전 리허설이 목적이다. 실제 대회처럼 보이는 가상의 주제와 규정(시간, 평가 항목, 제약)을 만들어 주되 **맨 위에 "연습용 가상 주제"라고 표시**한다. 가상의 규정이 실제 정보로 BRIEF에 남지 않도록, 사용자가 명시적으로 요청하지 않으면 BRIEF를 수정하지 않고 대화에만 출력한다. 이후 `contest-plan`, `contest-split`로 이어서 연습할 수 있게 한다.

## 끝낼 때

채운 항목과 `미정`으로 남은 항목을 구분해 보고하고, 다음 단계로 `contest-plan`을 제안한다. 아직 이슈나 코드를 만들지 않는다.
