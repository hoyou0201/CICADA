# 대회 계획 세우기

병렬 작업이 서로를 기다리게 되는 가장 흔한 원인은 **구현 전에 계약(입출력 형식)이 정해지지 않은 것**이다. 이 단계의 목표는 에이전트들이 사람별 담당 없이도 각자 가져가 끝낼 수 있도록 시간, 범위, 계약을 먼저 못 박는 것이다. 사람이나 에이전트에게 기능을 미리 배정하지 않는다. 일은 공용 풀이고 담당자는 일을 시작할 때 생기기 때문이다(`AGENTS.md`).

## 시작 전에 읽을 것

`AGENTS.md`와 `docs/BRIEF.md`. BRIEF의 "제품을 한 문장으로"가 비어 있으면 먼저 `contest-topic`을 쓰자고 말하고 멈춘다. 계획은 무엇을 만들지가 정해진 뒤에야 의미가 있다.

## 순서

1. **시간표.** 개발 시간 T를 받는다(모르면 묻는다). 기본 틀은 아래이고 실제 시각(시:분)으로 환산해서 보여 준다.

   | 구간 | 시점 | 내용 |
   |---|---|---|
   | 기획·계약 | 0 ~ 10% | 범위와 계약 합의 (이 스킬의 결과) |
   | 골격·첫 통합 | ~25% | 입력부터 결과까지 아주 얇은 흐름이 한 번 연결됨 |
   | 기능 구현 | 25% ~ 80% | 병렬로 완성. 30~45분마다 짧게 공유 |
   | 첫 배포 | ~50% | 배포가 되는지 한 번 확인 (마지막에 처음 배포하지 않는다) |
   | 새 기능 중단 | 80% | 이후는 통합, 오류·빈 결과 처리, 버그 수정 |
   | 발표 준비 | 마지막 15% | `docs/DEMO.md` 기준 리허설 |

2. **기능 목록(개수 제한 없음).** 기능을 몇 개로 할지 정해 두지 않는다. **우선순위 순으로** 나열하고 기능마다 정상 동작, 빈 결과, 오류 상태에서 **눈으로 확인 가능한 완료 조건**을 한 줄씩 쓴다. 범위는 개수가 아니라 시간으로 조절한다: 기능별 작업의 예상 시간 합이 (남은 시간 × 동시 작업 수)의 70%를 넘으면 범위가 크다고 알리고, 우선순위 낮은 순으로 자를 곳을 제안한다. "이번에 제외할 것"도 적는다. 동시 작업 수는 `.plankton.yml`의 용량 합이고, 없으면 사용자에게 묻는다.

3. **데이터·화면 계약.** 생산자, 소비자, 계약 파일 경로, 입력 필드와 타입, 성공·빈 결과의 예시, 실패 코드와 사용자 메시지, 샘플 데이터 경로를 정한다. 소비하는 쪽이 샘플로 먼저 연결할 수 있게 하고, 샘플과 실제 구현이 같은 계약을 쓰게 한다. 샘플을 쓰면 화면에도 표시한다.

4. **겹침 줄이기.** 작업이 서로 같은 파일을 건드리면 병렬의 이점이 사라진다. 공통 타입·라우트·전역 스타일·의존성·배포 설정은 골격 작업(T1)에서 미리 정리해서 이후 작업이 건드릴 일이 없게 한다는 방침을 세우고, 어쩔 수 없이 공유해야 하는 파일은 BRIEF에 적어 두어 `contest-split`이 그 파일을 쓰는 작업끼리 의존으로 순서를 정하게 한다.

5. **기술 선택안.** 주제가 정해졌으므로 이제 제안할 수 있다. 세 사람이 익숙한 기술을 사용자에게 묻고, 시간 내 완성과 배포 용이성을 기준으로 선택안과 이유를 적는다. 제안은 `(제안)`으로 표시하고 사용자가 확정하기 전에는 합의로 쓰지 않는다. 사전 코드나 외부 API가 규정상 허용인지 모르면 허용으로 가정하지 않는다.

## BRIEF 반영

"기능 목록", "시간표", "기술 결정", "데이터·화면 계약" 절을 채운다. 사용자가 확인한 것은 그대로, 내가 제안한 것은 `(제안)`으로 구분하고, 모르는 칸은 `미정`으로 둔다. "작업 이슈" 절은 `contest-split`이 채우므로 건드리지 않는다.

## 끝낼 때

시간표, 기능 목록과 완료 조건, 계약 요약, 확정이 필요한 질문(기술 선택 등)을 짧게 보고한다. 사용자가 계획을 승인하면 `contest-split`로 이어서 작업을 이슈로 나누자고 제안한다. 승인 전에는 이슈를 만들지 않는다.
