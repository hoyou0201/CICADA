# 대회 계획 세우기

병렬 작업이 서로를 기다리게 되는 가장 흔한 원인은 **구현 전에 계약(입출력 형식)이 정해지지 않은 것**이다. 이 단계의 목표는 사람별 담당 없이도 에이전트들이 각자 받은 일을 끝낼 수 있도록 시간, 범위, 계약을 먼저 못 박는 것이다. 사람이나 에이전트에게 기능을 미리 배정하지 않는다. 일은 공용 풀이고 담당자는 일을 시작할 때 생기기 때문이다(`AGENTS.md`).

## 시작 전에 읽을 것

`AGENTS.md`와 `docs/BRIEF.md`. BRIEF의 "제품을 한 문장으로"가 비어 있으면 먼저 `contest-topic`을 쓰자고 말하고 멈춘다. 계획은 무엇을 만들지가 정해진 뒤에야 의미가 있다.

## 순서

1. **시간표.** 개발 시간 T를 받는다(모르면 묻는다). 기본 틀은 아래이고 실제 시각(시:분)으로 환산해서 보여 준다.

   | 구간 | 시점 | 내용 |
   |---|---|---|
   | 기획·계약 | 0 ~ 10% | 범위와 계약 합의 (이 스킬의 결과) |
   | 골격·첫 통합 | ~25% | 입력부터 결과까지 아주 얇은 흐름이 한 번 연결됨 |
   | 기능 구현 | 25% ~ 80% | 병렬로 완성. 30~45분마다 짧게 공유 |
   | 첫 배포 | ~50% | 배포가 되는지 한 번 확인 (마지막에 처음 배포하지 않는다) |
   | 새 기능 중단 | 80% | 이후는 통합, 오류·빈 결과 처리, 버그 수정 |
   | 발표 준비 | 마지막 15% | `docs/DEMO.md` 기준 리허설 |

2. **기능 목록과 용량 맞추기.** 기능을 우선순위 순으로 나열하고 기능마다 정상 동작, 빈 결과, 오류 상태에서 **눈으로 확인 가능한 완료 조건**을 한 줄씩 쓴다. 그다음 아래 순서로 범위가 시간에 맞는지 점검한다. AI 에이전트는 일 하나를 몇 분 만에 끝내고 필요한 만큼 띄울 수 있으므로, 계획이 시간을 넘치는 것보다 **할 일이 떨어져 시간이 남는 것**이 더 흔한 실패다. 위아래 두 방향을 모두 점검한다.

   - **단위는 이슈 하나.** "일"은 `contest-split`이 만들 이슈 하나(PR 하나)다. 기능마다 split 규칙대로 몇 개의 이슈가 될지(보통 로직 / 화면 / 연결 / 마감 중 필요한 것, 2~4개)와 그 안에서 순서대로 이어지는 개수를 적는다. 이보다 잘게 센 숫자로 계산하지 않는다. 계획과 split의 단위가 다르면 계획에서 63개였던 일이 이슈 15개가 된다.
   - **두 숫자를 따로 센다.** **전체 일 수**는 모든 기능의 일을 더한 값이다. **경로 일 수**는 가장 길게 이어지는 의존 사슬의 일 개수다: 골격(T1) + 기능 중 가장 긴 사슬 하나 + 통합·배포 같은 마무리. 서로 의존하지 않는 기능의 일 수는 경로에 **누적하지 않는다**. 누적하면 전체 일 수가 되고, 실제로는 병렬로 끝나서 계획보다 훨씬 빨리 끝난다.
   - **에이전트 수는 고정값이 아니다.** 사용량이 허락하는 한 착수 가능한 일마다 에이전트를 새로 띄울 수 있다. 그래서 일이 많아도 시간은 거의 늘지 않고, **예상 완료 시간 = 경로 일 수 × 주기**다. 전체 일 수는 시간이 아니라 **사용량**을 정한다. 동시에 띄울 수 있는 에이전트에 상한이 있을 때만(사용량 한도, 사람이 띄울 수 있는 수) `max(경로 일 수 × 주기, 전체 일 수 × 주기 ÷ 상한)`으로 계산한다. 상한을 모르면 "제한 없음"으로 두고 대회 중 리더가 사용량을 보고 정한다.
   - **주기**는 일을 지시한 시각부터 PR이 병합되는 시각까지다. BRIEF 시간표의 "일 1개 주기"를 쓰고 `미정`이면 **3분으로 가정**하며 "가정값"이라고 알린다(연습에서 Codex·Claude는 이슈 하나를 3분 안팎에 끝냈다). 연습 전체 시간(이슈 12개에 43분)은 중간에 키트를 고치느라 빈 시간과 느린 에이전트가 섞여 있어서 주기 근거로 쓰지 않는다. 대회 중에는 리더가 실측 주기로 바꿔 보고한다. 에이전트에게 일마다 시간을 추정하게 하지 않는다.
   - **확정 범위(첫 묶음).** 핵심 흐름이 배포본에서 동작하는 데 꼭 필요한 기능까지를 확정 범위로 하고, 예상 완료가 **개발 시간의 50%(첫 배포) 안**에 들어와야 한다. 넘으면 우선순위 낮은 순으로 스트레치로 내린다.
   - **시간은 쌓는 사슬로 채운다(하한 점검).** 에이전트를 늘리면 폭은 공짜이므로, 일을 옆으로 더 늘려도 시간은 채워지지 않는다. 시간을 쓰는 것은 **앞 결과 위에 차례로 쌓이는 일의 사슬**이고, 묶음은 그 사슬을 층으로 나눠 본 것이다. 묶음 하나는 기능 몇 개를 병렬로 만들고 → 통합 → 배포본 점검까지이고, 점검에서 나온 문제와 다듬을 점이 다음 묶음의 맨 위 후보가 된다. **스트레치가 끝나는 시점 = 기획 끝 + 모든 후보를 잇는 가장 긴 의존 사슬의 일 수 × 주기**다. 사슬은 T1 → 기능 → 그 위에 쌓은 후보 → … → 마지막 점검처럼 쌓는 관계와 파일 겹침을 따라 센다. 묶음별 시간을 차례로 더하지 않는다. 이슈는 처음에 모두 만들고 필요한 의존만 걸기 때문에 묶음은 차례로 끝나지 않고 겹쳐서 진행되며, 묶음 시간을 더하면 실제보다 두 배 이상 늦게 나온다(연습: 묶음 합산 T+169, 실제 이슈 그래프 경로 17단계 = T+81). 이 시점을 새 기능 중단 시점과 비교한다.
     - **후보 하나가 묶음 하나가 아니다.** `contest-split`은 수정 경로가 겹치지 않고 아직 안 끝난 일에 기대지 않는 후보를 **한 묶음에 모두** 담는다. 그래서 후보가 채우는 묶음 수는 후보를 위에서부터 "들어갈 수 있는 가장 이른 묶음"에 배치해 보고 나온 묶음 개수다. 배치 결과를 표에 "묶음" 열로 적는다(예: 스트레치 1~6은 서로 겹치지 않으면 모두 묶음 2). **묶음 2보다 뒤에 놓은 후보에는 이유를 적는다**: 어느 후보 위에 쌓는지(예: "스트레치 10 위") 또는 어느 파일이 겹치는지. 이유를 적을 수 없으면 그 후보는 묶음 2다. 시간을 채우려고 독립 후보를 뒤 묶음으로 흩어 놓지 않는다. 묶음이 늦게 생기는 이유는 둘뿐이다: 앞 묶음의 결과 위에 쌓는 후보(예: 묶음 2의 편집 기능 위에 묶음 3의 일괄 편집)이거나, 같은 파일을 고쳐야 하는 후보다.
     - 스트레치가 끝나는 시점이 새 기능 중단보다 이르면, 후보를 옆으로 더 늘리지 말고 **앞 묶음 위에 쌓는 후보**를 더 뽑는다. 각 묶음의 배포본 점검에서 나올 수정·다듬기 몫도 다음 묶음에 한 줄씩 넣는다. 그래도 모자라면 일찍 끝난다고 보고하고, 남는 시간을 어디에 쓸지(제품 범위를 키울지, 점검·다듬기를 반복할지) 사용자가 정하게 한다. **사용량도 함께 본다.** 전체 일 수가 늘면 띄울 에이전트와 사용량이 늘어나므로, 시간을 다 채우려고 후보를 억지로 늘리지 않는다. 연습 기준 이슈 90개 안팎이면 충분하고, 그보다 크게 잡을 때는 사용량을 사용자에게 확인한다.
     - 새 기능만이 아니라 **깊이**도 후보다: 기존 기능의 오류·빈 결과 다듬기, 디자인·반응형, 테스트, 데모용 데이터와 연출, 배포본 점검 후 버그 수정. 후보는 계획 시점에 근거와 순서가 있어야 대회 중에 바로 이슈로 바꿀 수 있다. 한 묶음에 담는 기능 수는 에이전트 수가 아니라 **수정 경로가 겹치지 않는 범위와 사용량**이 정한다.
   - 예: 개발 5시간(300분), 주기 3분, 에이전트 상한 없음. 이슈 15개·경로 5단계인 확정 범위는 15분이면 끝난다(기획 10%인 30분 시점에 시작하면 45분 시점). 새 기능 중단(240분)까지 195분이 남는다. 이를 채우려면 **가장 긴 의존 사슬이 약 65단계**(195 ÷ 3)여야 한다. 연습에서 이슈 92개를 만들었을 때도 사슬은 17단계였다. 이슈를 15개에서 100개로 늘려도 경로가 5단계면 여전히 15분 만에 끝난다. 서로 겹치지 않는 스트레치 후보 10개는 묶음 10개가 아니라 묶음 1~2개를 채울 뿐이다.

   보고할 때 확정 범위의 경로 일 수·전체 일 수·예상 완료 시간, 배치해 본 묶음 수, 모든 후보를 잇는 가장 긴 사슬의 일 수, 스트레치가 끝나는 시점과 새 기능 중단까지 남는 시간을 함께 알린다. "이번에 제외할 것"도 적는다.
3. **데이터·화면 계약.** 생산자, 소비자, 계약 파일 경로, 입력 필드와 타입, 성공·빈 결과의 예시, 실패 코드와 사용자 메시지, 샘플 데이터 경로를 정한다. 소비하는 쪽이 샘플로 먼저 연결할 수 있게 하고, 샘플과 실제 구현이 같은 계약을 쓰게 한다. 샘플을 쓰면 화면에도 표시한다.

4. **겹침 줄이기.** 작업이 서로 같은 파일을 건드리면 병렬의 이점이 사라진다. 공통 타입·라우트·전역 스타일·의존성·배포 설정은 골격 작업(T1)에서 미리 정리해서 이후 작업이 건드릴 일이 없게 한다는 방침을 세우고, 어쩔 수 없이 공유해야 하는 파일은 BRIEF에 적어 두어 `contest-split`이 그 파일을 쓰는 작업끼리 의존으로 순서를 정하게 한다.

5. **디자인.** 완성도와 시연 효과는 화면에서 바로 보이므로 디자인을 막판 다듬기 한 줄로 두지 않는다. 디자인도 Claude Code 같은 작업 에이전트가 이슈로 하므로, 일을 줄 수 있게 이슈 단위로 계획한다.
   - **방향.** 톤(예: 따뜻한·차분한), 색(주요색, 상태색), 글꼴, 간격·모서리 같은 스타일 규칙과 참고할 화면 1~2개를 BRIEF "디자인" 절에 `(제안)`으로 적는다. 1분 데모에서 첫인상을 정하는 화면 하나를 정한다.
   - **토큰은 T1에서.** T1 골격이 디자인 토큰 파일(색·글꼴·간격을 CSS 변수 등으로)과 이름을 먼저 만든다. 기능 화면은 처음부터 이 이름만 쓰고 색 값을 직접 쓰지 않는다. 그래야 나중에 값을 바꿔도 화면 파일을 다시 고치지 않는다.
   - **디자인 시스템 이슈 하나를 묶음 1에.** 토큰 값과 기본 컴포넌트(버튼·입력·카드·배지 등)를 채우는 일이다. T1에만 의존하고 기능 이슈들과 동시에 진행한다. 기능 이슈가 이 일을 기다리지 않게 한다(토큰 이름은 T1에 있으므로).
   - **기능마다 디자인 다듬기를 그 기능 위에 쌓는다.** 화면이 있는 기능은 "기능 연결 → 그 화면 디자인 다듬기" 순서로 디자인 일을 하나 둔다. 수정 경로는 그 기능의 화면 파일과 스타일 파일로 한정해 다른 기능과 겹치지 않게 한다. 이 일은 앞 결과 위에 쌓는 후보이므로 묶음 배치에서 그 기능의 다음 묶음에 들어간다.
   - 전체를 한 번에 바꾸는 디자인 일(전역 레이아웃, 반응형 전수 점검)은 모든 화면 파일과 겹치므로 수를 최소로 하고 묶음 배치에 겹침 이유를 적는다.
   - 디자인 일도 기능 목록의 일 수·사슬·묶음 배치에 넣는다. 기능 목록 표에 디자인 시스템과 기능별 디자인 다듬기를 별도 줄로 적고, 2단계의 예상 완료와 스트레치가 끝나는 시점을 다시 계산한다.

6. **기술 선택안.** 주제가 정해졌으므로 이제 제안할 수 있다. 세 사람이 익숙한 기술을 사용자에게 묻고, 시간 내 완성과 배포 용이성을 기준으로 선택안과 이유를 적는다. 제안은 `(제안)`으로 표시하고 사용자가 확정하기 전에는 합의로 쓰지 않는다. 사전 코드나 외부 API가 규정상 허용인지 모르면 허용으로 가정하지 않는다.

## BRIEF 반영

"기능 목록", "시간표", "기술 결정", "데이터·화면 계약", "디자인" 절을 채운다. 기능 목록에는 기능마다 일 수와 사슬 길이를 적고, 확정 범위와 스트레치의 경계를 표시한다. 사용자가 확인한 것은 그대로, 내가 제안한 것은 `(제안)`으로 구분하고, 모르는 칸은 `미정`으로 둔다. "작업 이슈" 절은 `contest-split`이 채우므로 건드리지 않는다.

## 끝낼 때

시간표, 기능 목록과 완료 조건, 확정 범위의 예상 완료 시간, 스트레치가 끝나는 시점, 계약 요약, 디자인 방향, 확정이 필요한 질문(기술 선택 등)을 짧게 보고한다. 사용자가 계획을 승인하면 `contest-split`로 이어서 모든 묶음을 이슈로 나누자고 제안한다. 승인 전에는 이슈를 만들지 않는다.
