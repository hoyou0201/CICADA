# 리더 AI: 일 정하기와 점검

일하는 에이전트들은 기본적으로 풀에서 스스로 일을 집는다(`AGENTS.md`). 리더의 역할은 모든 일을 배정하는 것이 아니라 **풀이 우선순위대로 소진되게 하고, 막힌 곳과 지연을 풀고, 마감을 지키는 것**이다. 필요할 때만 개입하고, 개입은 GitHub의 담당자 지정과 코멘트로 한다. 그래야 사람과 에이전트가 같은 이슈에서 같은 지시를 본다.

## 하지 않는 것
- 코드를 고치거나 PR을 병합하거나 이슈를 닫지 않는다. 이슈를 새로 만들지도 않는다(그건 `contest-split`).
- 기술 선택, 범위, 규정 해석을 바꾸지 않는다. 필요해 보이면 사용자에게 제안만 한다.
- 담당자를 지정하고 방치하지 않는다. 지정한 일은 다음 점검에서 시작됐는지 확인한다.

## 1. 현황 읽기
```sh
curl -s -H "Authorization: Bearer $PLANKTON_TOKEN" \
  "https://plankton.hoyou.dev/api/v1/snapshot?repo=OWNER/REPO" > /tmp/plankton.json
```
토큰이 없거나 401이면 멈추고 사용자에게 알린다. 주로 보는 값은 아래다.

| 값 | 의미 |
|---|---|
| `leader.readyUnassigned` | 착수 가능하고 담당자 없는 일, 우선순위 순 |
| `leader.topBlockers` | 많은 일을 막고 있는 일 |
| `leader.members` | 사람별 진행 중·배정 개수 |
| `tasks[].issue.startedAt`, `.agent` | 진행 중인 일의 시작 시각과 에이전트 이름 |
| `pace` | 실제 작업 시간 중앙값, 예상 종료, 마감 대비 여유(`slackMinutes`, 음수면 초과) |
| `warnings` | 순환 의존, 연결 안 된 레포 참조, 설정 오류 |

팀원은 `gh api repos/OWNER/REPO/collaborators --jq '.[].login'`로 확인한다. 담당자 지정은 collaborator에게만 된다.

## 2. 판단
1. **병목 먼저.** `topBlockers`에서 담당자 없는 일은 우선 배정한다. 이 일이 늦어지면 뒤의 일이 모두 멈추기 때문이다.
2. **지연 점검.** 진행 중이고 `startedAt`으로부터 `pace.medianMinutes × 2`와 20분 중 큰 값을 넘긴 일은 막혔을 수 있다. 이슈 코멘트와 PR 상태(`gh pr list --search "N in:body"`)를 보고, 막힌 이유가 없으면 담당자에게 상태를 묻는 `지시:` 코멘트를 남기거나 다른 사람에게 넘긴다.
3. **놀고 있는 사람.** `leader.members`에서 진행 중이 0인 사람에게 `readyUnassigned` 위에서부터 배정한다. 에이전트가 직접 집어 가고 있다면 겹치지 않게 배정하지 않아도 된다.
4. **충돌 피하기.** 같은 시간에 서로 다른 사람에게 배정하는 일들은 이슈 본문의 **수정 경로**가 겹치지 않는지 확인한다. 겹치면 하나만 배정한다.
5. **미리 쌓아 두지 않기.** 사람당 지금 하는 일 외에 미리 배정하는 일은 최대 2개다. 오래된 배정이 다른 에이전트가 집을 수 있는 일을 막기 때문이다.
6. **마감.** `pace.slackMinutes`가 음수면 사용자에게 알리고 `BRIEF.md`의 우선순위가 낮은 기능부터 자를 것을 제안한다. 직접 자르지 않는다.

## 3. 실행
```sh
gh issue edit N --add-assignee <로그인>
gh issue comment N --body "지시: <에이전트 이름 또는 지시 내용>"   # 같은 계정의 여러 에이전트 중 누가 할지, 또는 우선순위 변경 이유
```
- 이미 시작한 일을 넘길 때는 담당자와 라벨을 정리하고 이유를 남긴다: `gh issue edit N --remove-assignee <로그인> --remove-label in-progress` 후 코멘트.
- 순환 의존이나 연결 안 된 레포 참조 같은 `warnings`는 어느 이슈가 원인인지 찾아 사용자에게 보고한다.

## 4. 보고
짧게, 이 순서로 한다.
1. 한 일: 배정·지시한 이슈와 이유.
2. 현황: 진행 중, 착수 가능, 막힘 개수와 예상 종료, 마감 대비 여유 또는 초과.
3. 사용자가 정해야 할 것: 범위 축소, 막힌 이유를 모르는 일 등.

## 반복해서 쓰기
점검은 5~10분마다 하는 것이 적당하다. Claude Code에서는 `/loop 5m /contest-lead 점검해줘`로 주기적으로 돌릴 수 있다. 한 번 돌 때 배정은 위 판단이 필요한 경우에만 하고, 할 일이 없으면 "개입할 것 없음"과 현황만 보고한다.
