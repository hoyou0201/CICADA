# 리더 AI: 일 정하기와 점검

작업 에이전트는 **리더가 준 일 하나만 하고 멈춘다**(`AGENTS.md`). 풀에서 스스로 고르지 않으므로, 리더가 일을 주지 않으면 아무도 일하지 않는다. 리더의 역할은 **놀고 있는 에이전트에게 우선순위대로 다음 일을 주고, 막힌 곳과 지연을 풀고, 마감을 지키는 것**이다. 일을 주는 방법은 GitHub의 담당자 지정과 `지시:` 코멘트다. 그래야 사람과 에이전트가 같은 이슈에서 같은 지시를 본다.

## 하지 않는 것
- 코드를 고치거나 PR을 병합하거나 이슈를 닫지 않는다. 이슈를 새로 만들지도 않는다(그건 `contest-split`). 일이 모자라면 사용자에게 알린다.
- 기술 선택, 범위, 규정 해석을 바꾸지 않는다. 필요해 보이면 사용자에게 제안만 한다.
- 담당자를 지정하고 방치하지 않는다. 지정한 일은 다음 점검에서 시작됐는지 확인한다.

## 1. 현황 읽기
```sh
curl -s -H "Authorization: Bearer $PLANKTON_TOKEN" \
  "https://plankton.hoyou.dev/api/v1/snapshot?repo=OWNER/REPO" > /tmp/plankton.json
```
토큰이 없거나 401이면 멈추고 사용자에게 알린다. 주로 보는 값은 아래다.

| 값 | 의미 |
|---|---|
| `leader.readyUnassigned` | 착수 가능하고 담당자 없는 일, 우선순위 순 |
| `leader.topBlockers` | 많은 일을 막고 있는 일 |
| `leader.members` | 사람별 진행 중·배정 개수 |
| `tasks[].issue.startedAt`, `.agent` | 진행 중인 일의 시작 시각과 에이전트 이름 |
| `pace` | 실제 작업 시간 중앙값, 예상 종료, 마감 대비 여유(`slackMinutes`, 음수면 초과) |
| `warnings` | 순환 의존, 연결 안 된 레포 참조, 설정 오류 |

팀원은 `gh api repos/OWNER/REPO/collaborators --jq '.[].login'`로 확인한다. 담당자 지정은 collaborator에게만 된다.

## 2. 판단
0. **가동 중인 에이전트 파악.** 에이전트는 자기가 일을 끝내면 멈추므로, 누가 놀고 있는지 알려면 이름 목록이 필요하다. 처음 한 번 사용자에게 가동 중인 에이전트 이름과 각각의 소유자 GitHub 아이디를 묻는다(예: `claude-code/w1` — hoyou0201). 이슈의 `시작: <이름>` 코멘트 이력(`tasks[].issue.agent`)도 참고한다.
1. **놀고 있는 에이전트 찾기.** 지시한 일이 닫혔거나 아직 지시한 일이 없는 에이전트다. 각각에게 다음 일을 준다. 에이전트 수는 고정이 아니다. 착수 가능한 일이 놀고 있는 에이전트보다 많으면 **에이전트를 몇 개 더 띄우면 되는지**와 새 이름(`claude-code/w5`처럼 겹치지 않게)을 제안하고, 그 이름으로 바로 지시해 둔다. 사용자가 사용량 한도를 말했으면 그 안에서만 늘린다.
2. **무엇을 줄지.** `leader.topBlockers`에서 담당자 없는 일(많은 일을 막는 일)을 먼저, 그다음 `leader.readyUnassigned` 위에서부터. 막혀 있는(열린 blocker가 있는) 일은 주지 않는다. **빠른 에이전트에게 경로 위의 일을 준다.** 다른 일을 막는 일은 끝난 일의 실제 시간이 짧은 에이전트(보통 Codex·Claude)에게 주고, 느린 에이전트에게는 아무것도 막지 않는 일(끝 단계, 다듬기)을 준다. 느린 에이전트가 경로 위의 일을 잡으면 전체 완료가 그만큼 밀린다. 사용자가 디자인을 맡길 에이전트를 정했으면 `디자인` 라벨 일은 그 에이전트에게 먼저 준다.
3. **충돌 피하기.** 동시에 지시하는 일들은 이슈 본문의 **수정 경로**가 겹치지 않는지 확인한다. 겹치면 하나만 준다.
4. **에이전트당 지시는 1개.** 미리 쌓아 두지 않는다. 에이전트가 하나를 끝내면 멈추기 때문에 쌓아 둬도 소용없고, 오래된 지시가 다른 에이전트가 맡을 수 있는 일을 막는다.
5. **지연 점검.** 진행 중이고 `startedAt`으로부터 `pace.medianMinutes × 2`와 20분 중 큰 값을 넘긴 일은 막혔을 수 있다. 이슈 코멘트와 PR 상태(`gh pr list --search "N in:body"`)를 보고, 막힌 이유가 없으면 담당 에이전트에게 상태를 묻는 `지시:` 코멘트를 남기거나 다른 에이전트에게 넘긴다.
6. **마감.** `pace.slackMinutes`가 음수면 사용자에게 알리고 `BRIEF.md`의 우선순위가 낮은 기능부터 자를 것을 제안한다. 직접 자르지 않는다.
7. **남는 시간.** 모든 묶음의 이슈는 처음에 만들어져 있다. 열린 일 중 남은 가장 긴 의존 사슬 × 주기로 끝나는 시점을 구한다(에이전트를 늘릴 수 있으므로 남은 시간은 일 개수가 아니라 남은 사슬이 정한다). 이 시점이 새 기능 중단(80%)보다 30분 이상 이르면 사용자에게 알리고 BRIEF의 "시간이 남을 때" 선택지를 제안한다.
   - 주기는 최근 닫힌 일들의 `지시:` 코멘트 시각부터 닫힌 시각까지의 중앙값으로 잰다. 이 값을 BRIEF 시간표의 "일 1개 주기"와 비교해 크게 다르면 보고에 적는다(갱신은 사용자가 정한다).

## 3. 실행
```sh
gh issue edit N --add-assignee <로그인>
gh issue comment N --body "지시: <에이전트 이름> — 선행 #A, #B 닫힘 확인. <한 줄 메모>"   # 이름이 필수다. 같은 계정의 여러 에이전트 중 누가 할지 정한다
```
- **주기 전에 반드시 착수 가능한지 확인한다.** `tasks[]`에서 그 이슈의 `state`가 `ready`이고 `blockers`가 비어 있어야 한다. 지시 코멘트에 "선행 #N 닫힘 확인"을 적는 것은 작업 에이전트가 선행 이슈를 다시 조사하지 않고 이 코멘트를 믿고 바로 시작하게 하려는 것이다. 선행이 없는 일은 "선행 없음"이라고 적는다.
- 이미 시작한 일을 넘길 때는 담당자와 라벨을 정리하고 이유를 남긴다: `gh issue edit N --remove-assignee <로그인> --remove-label in-progress` 후 코멘트.
- 순환 의존이나 연결 안 된 레포 참조 같은 `warnings`는 어느 이슈가 원인인지 찾아 사용자에게 보고한다.

## 4. 보고
짧게, 이 순서로 한다.
1. 한 일: 배정·지시한 이슈와 이유. **어느 에이전트를 다시 실행해야 하는지**와 그 에이전트에게 붙여 줄 한 줄(`docs/PROMPTS.md`의 작업 에이전트 프롬프트)을 함께 알린다. 에이전트는 지시를 받아도 사용자가 실행해야 움직인다.
2. 현황: 진행 중, 착수 가능, 막힘 개수와 예상 종료, 마감 대비 여유 또는 초과, 실측 주기, 지금 더 띄우면 좋은 에이전트 수.
3. 사용자가 정해야 할 것: 범위 축소, 남는 시간을 쓸 곳, 막힌 이유를 모르는 일 등.

## 반복해서 쓰기
보통은 사용자가 "일 배정해줘"라고 할 때 부른다. 부를 때마다 위 판단을 한 번 한다. 원하면 Claude Code에서 `/loop 5m /contest-lead 점검해줘`로 주기적으로 돌릴 수도 있다. 한 번 돌 때 배정은 위 판단이 필요한 경우에만 하고, 할 일이 없으면 "개입할 것 없음"과 현황만 보고한다.
