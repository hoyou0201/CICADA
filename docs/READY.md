앱 스택을 선택하면 세 명의 버전을 맞추고 실행 방법을 기획서에 기록한다.

## 함께 할 30분 리허설 · 규정 확인 후 연습용 저장소에서

1. 0~5분: 세 명이 clone, 개인 브랜치 생성, AI 규칙 요약 확인.
2. 5~12분: 서로 다른 파일에 작은 연습 변경 하나씩 만들고 커밋·push·PR.
3. 12~18분: 한 명이 검토·반영하고, 나머지는 main 변경을 자기 브랜치에 merge.
4. 18~23분: 연습 브랜치의 같은 텍스트 줄을 다르게 고쳐 충돌을 한 번 경험하고 함께 해결.
5. 23~30분: 선택한 스택의 작은 샘플을 배포하고 다른 두 명이 새 브라우저에서 접속.

시연 URL과 검증자는 [STATUS.md](STATUS.md)에 기록한다. 샘플은 대회 출품물과 구별한다.
규정이 사전 코드를 금지하면 연습 결과를 출품 저장소에 가져가지 않는다.

## 계정·배포·비상 준비

- [ ] GitHub 저장소에 B/C 초대와 쓰기 권한 적용 완료; PR 하나로 실제 확인
- [ ] 팀 대화 채널, 실명/역할, 발표자·시연자 결정
- [ ] 배포 담당·서비스·로그인·플랜 제한·결제 필요 여부 확인 후 연습 배포
- [ ] 실제 서비스 URL에서 HTTPS·새로고침·모바일 폭·핵심 기능 확인
- [ ] 외부 API가 필요하면 키 소유자·요금 한도·서버 저장 위치·호출 실패 대안 결정
- [ ] 공개 클라이언트 설정과 서버 전용 비밀값 구분, `.env.example`은 빈 값으로 공유
- [ ] 충전기·멀티탭·핫스팟·화면 공유·제출 계정 로그인 준비
- [ ] 외부 서비스 장애 시 보여 줄 표시된 샘플 데이터·영상의 규정 허용 여부 확인

주제가 웹 서비스일 경우, 팀이 아는 UI 도구 + 필요한 최소 서버 기능을 우선 검토한다.
게임·모바일·특정 플랫폼이 요구되면 해당 스택으로 바꾼다. 프레임워크와 DB는 아직 확정하지 않는다.
