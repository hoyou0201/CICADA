# 대회 당일·데모·제출

아래 비율은 제한 시간을 모르는 상태의 운영 초안이다. 공식 일정에 맞춰 시각을 [기획서](BRIEF.md)에 적는다.

| 전체 개발 시간 | 목표 |
| --- | --- |
| 0~10% | 규정·주제 확인, 문제와 핵심 흐름 하나, 역할·스택·계약 합의 |
| 10~25% | 가장 얇은 전체 흐름을 연결하고 첫 배포 시도 |
| 25~65% | 분담 기능 구현과 작은 PR 통합, 실제 데이터 연결 |
| 65~80% | 기능 연결·빈 결과/오류·모바일 폭·새로고침 확인 |
| 80~90% | 새 기능 중단, 발표·시연 연습과 치명적 오류 수정 |
| 90~100% | 제출·URL 확인·허용된 백업 확보 |

## 시연 대본 · 발표 시간에 맞게 조절

1. 문제: 누가 어떤 상황에서 불편한가? (15초 예시)
2. 해결: 제품이 해주는 핵심 동작 한 문장. (15초 예시)
3. 실제 시연: 입력 → 핵심 처리 → 사용자가 얻는 결과. (60초 예시)
4. 차이와 근거: 주제에 어떻게 맞고 무엇을 개선하는가? 실제 측정·관찰만 사용. (20초 예시)
5. 한계와 다음 단계: 구현한 범위와 남은 범위를 짧게 구분. (10초 예시)

발표자: 미정 / 시연자: 미정 / 시연 입력·계정·데이터: 미정.
화면을 켜두는 사람과 설명하는 사람을 분리하면 시연 중 조작 실수를 줄일 수 있다.

## 최종 확인

- [ ] 배포된 URL을 다른 팀원 기기의 새 브라우저에서 열고 전체 핵심 흐름 수행
- [ ] 새로고침·직접 경로 접속·키보드·발표 화면 크기·모바일 폭 확인
- [ ] 입력 오류·빈 결과·API 장애·로딩 중 상태 확인, 무한 대기 없음
- [ ] 샘플 데이터면 UI에 표시, 실제 서비스와 구분해서 설명
- [ ] README에 설치·실행·환경 변수 이름·한계·실제 검증 결과 기록
- [ ] 공식 평가 항목마다 시연에서 보여 줄 장면 대응
- [ ] 제출 커밋 SHA·배포 버전·URL·제출 파일/제목 일치 확인
- [ ] 공개 범위·비밀값·출처·라이선스·AI 사용 증빙 요구 확인
- [ ] 공식 제출 페이지에서 접수 완료 상태 확인, 팀원 한 명이 제출 링크 재확인

## 장애가 생기면

| 상황 | 대응 |
| --- | --- |
| AI 한도 도달·응답 지연 | 인수인계 텍스트와 현재 diff를 남기고 사용 가능한 도구 또는 사람이 이어서 작업 |
| 외부 API 장애 | 타임아웃 후 오류 안내. 허용된 경우 명확히 표시한 샘플 흐름으로 전환 |
| 배포 실패 | 마지막 정상 배포 유지, 원인 수정 후 재시도. 로컬 실행 대안의 규정 허용 여부 확인 |
| Git 충돌 | 해당 담당자와 한 명씩 해결하고 검사 재실행. 무관한 변경을 지우지 않음 |
| 네트워크 장애 | 핫스팟·사전 확인한 로컬 실행. 영상은 규정 허용 때만 대체 자료로 사용 |
| 시간이 부족함 | 필수 흐름을 유지하면서 저장·공유·장식 등 미완료 부가 범위를 축소 |

마지막 정상 커밋/배포: 미정. 제출 후 확인자/접수 시각: 미정.
